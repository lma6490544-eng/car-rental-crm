# Числовые идентификаторы

Этап 3, 13 ноября: `pricing_quotes` получает отдельную identity-последовательность и числовой self-FK; аудит расширен типом `pricing_quote` (миграции 0006–0007). Общая последовательность не возвращается, ID существующих записей не меняются. [Описание](stage-3.md).

Актуально после миграции `0005_quiet_impossible_man.sql`: у каждой таблицы с числовым ID своя identity-последовательность, общая `record_id_seq` удалена. Все существующие ID сохранены; счётчик продолжает с максимального ID своей таблицы. Аудит хранит обязательный `entity_type` (`user`, `customer`, `vehicle`) и читает историю по типу + ID. Ниже описание 0004 сохранено как история первоначального перехода. Рациональность текущей схемы и рекомендации: [проверка схемы](schema-review-2026-11-12.md).

Миграция 0005 применена к локальной базе 12 ноября 2026. Перед применением создана `.local/pre-table-identities-2026-11-12.sql` (приватная резервная копия). Проверено: 13 отдельных identity-столбцов, общей последовательности нет, все события аудита имеют тип; ID автомобилей 1200–1203 сохранены. Тест миграции проверяет сохранение всех строк, независимость счётчиков, одинаковые ID разных сущностей, параллельное создание и повторный seed. Серверные тесты этапа 1 и полный API/browser-прогон этапа 2 прошли. Ранее найденная ошибка порога ТО исправлена: начальное значение — текущий пробег + 10000, ручное значение сохраняется при переключении процедуры.

12 ноября 2026 года пользователь разрешил заменить UUID записей числовыми ID. Изменены таблицы, внешние ключи, API, DTO, типы frontend, глубокие ссылки после входа и seed. API возвращает ID как JSON number; ссылки имеют вид `/fleet/1202`, `/clients/1100`.

Применена миграция `0004_skinny_sharon_carter.sql`. Она строит единую временную таблицу соответствия UUID → integer, переносит все ссылки, включая полиморфный entity_id аудита, ID внутри JSON истории/результатов команд/outbox и ключи событий. Перенос выполняется транзакционно; внешние ключи восстанавливаются. У всех записей используется общая последовательность record_id_seq с началом 10000; диапазон 1000–1999 используется стабильными тестовыми записями. Глобальная уникальность автоматически выдаваемых ID сохраняет однозначность истории разных сущностей.

Существующие записи не удалены. Пароли, сессионные секреты, ключи идемпотентности и UUID requestId для трассировки не изменяются. Резервная копия базы до перехода: `.local/pre-numeric-ids-2026-11-12.sql` (содержит приватные данные, не публиковать).

После перехода открытые страницы нужно обновить и перейти в карточки из списка. Старые UUID-ссылки больше не поддерживаются. Неопределённый результат команды до миграции можно найти по прежнему ключу через `/operations/by-key`: результат уже содержит числовой ID. Старый fingerprint запроса сохранён для аудита; изменённый числовой payload нельзя повторно отправлять со старым ключом — при необходимости сначала проверить результат, затем для нового изменения использовать новый ключ.

Проверки: TypeScript и production-сборка прошли; отдельный тест `npm.cmd run test:ids` подтвердил миграцию заполненной UUID-базы с сохранением FK, истории, приватных текстов, сессий, пароля, outbox и прежних результатов. 10 серверных сценариев авторизации прошли. Основные сценарии этапа 2 прошли, но браузерный сценарий предзаполнения ТО выявил восстановление старого значения при появлении поля: исправлен порядок обновления. В браузерном тесте сотрудников исправлено преждевременное утверждение до загрузки строки. Повторный браузерный прогон был отклонён пользователем; эти исправления повторно браузером не подтверждены.

Документы целевой архитектуры и первоначальные отчёты этапов со ссылками на UUID читаются с этим изменением.
