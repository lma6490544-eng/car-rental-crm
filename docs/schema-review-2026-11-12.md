# Проверка фактической схемы БД — 12 ноября 2026

Область: 15 таблиц `apps/api/src/db/schema.ts`, миграции 0000–0005, SQL чтения и записи текущего API. Будущие брони, договоры и финансы из `data-model.md` пока не реализованы и не оцениваются как существующая схема.

## Вывод

Для текущего этапа схема в целом соразмерна задаче. PostgreSQL, обычные внешние ключи и транзакции достаточны. Перепроектировать всё или дробить на дополнительные универсальные сущности не нужно. Основные долги — следы изменений требований, неполный аудит клиентов и инфраструктура событий, для которой ещё нет обработчика.

## Исправлено в этой задаче

- Все 13 таблиц с числовым `id` получили собственный `GENERATED BY DEFAULT AS IDENTITY`. Миграция 0005 сохраняет ID и FK; следующая выдача начинается с `max(id)+1`, для пустой таблицы — с 1. Общая последовательность удалена.
- `audit_logs.entity_type` обязателен: `user`, `customer`, `vehicle`. Существующие события классифицируются по пространству имён действия; неизвестное действие останавливает миграцию, а не получает выдуманный тип.
- Все места записи передают тип явно. История выбирается по паре `(entity_type, entity_id)`; соответствующий индекс включает время и ID события для устойчивой сортировки.
- Заметки клиента и процедуры обслуживания остаются событиями родительской карточки. Их собственные ID записаны в details; это намеренно, чтобы видеть историю карточки целиком.
- `login_limits` сохраняет смысловой строковый ключ, таблица связи `equivalence_group_models` — уникальную пару FK. Искусственный числовой ID этим двум таблицам не нужен.
- Seed с фиксированными демонстрационными ID сдвигает соответствующие счётчики под блокировкой таблиц. Повторный запуск не перезаписывает данные.

## Что оставить

| Решение | Обоснование |
| --- | --- |
| Марка → модель → автомобиль | Не дублирует названия; позволяет автоматически добавлять справочники и использовать модель в подборе автомобиля. |
| Тарифная группа модели отдельно от группы аналогов | Цена и допустимая замена — разные понятия. Объединение потеряет смысл. |
| FK без каскадного удаления деловых данных | Не позволяет незаметно удалить связанные записи; архив автомобиля сохраняет историю. |
| Версия клиента и автомобиля | Защищает от потери параллельных правок. Версия родителя также сериализует изменения его заметок/обслуживания; отдельные версии дочерних записей пока не нужны. |
| Текущий пробег и порог ТО в автомобиле, выполненные работы в журнале | Текущее состояние отличается от исторического факта. Исправление старой процедуры не должно автоматически откатывать пробег автомобиля. |
| JSONB реквизитов клиента | При двух формах и отсутствии поиска по паспортным/банковским реквизитам приемлемо; Zod проверяет структуру, списки не возвращают реквизиты. Для поиска, отчётов или раздельных прав доступа нужные поля можно выделить позднее. |
| Сессии и идемпотентность в PostgreSQL | Решают конкретные задачи выхода/отзыва доступа и безопасного повтора команд без отдельного сервиса. |
| Полиморфная ссылка в аудите | Удобна для разных типов событий. Обычный FK на несколько таблиц невозможен; тип ограничен CHECK, автор имеет FK. Аудит должен переживать жизненный цикл сущности. Это не схема для связей между бизнес-таблицами. |

## Рекомендуемые следующие изменения (не внесены)

### Приоритет 1 — устранить несоответствия текущим требованиям

1. **Одна физическая пометка автомобиля.** UI уже использует `note`, но БД хранит `readiness_reason` и `issue_notes`, а API склеивает их и раскладывает по готовности. Перенести имеющиеся тексты в одно `note`, сохранить CHECK «не готов → непустая пометка», удалить совместимые старые поля DTO после согласованного перехода. Сейчас изменение готовности меняет место хранения одного и того же текста и усложняет код.
2. **Дата обслуживания — `date`, а не `text`.** API проверяет ISO-дату, но сама БД допускает произвольную строку. При переводе сохранить строковый контракт API `YYYY-MM-DD` и не вносить часовой пояс в календарную дату. Проверить старые значения перед преобразованием.
3. **Полноценные изменения в аудите клиента.** `customers.updated` записывает только список присланных полей, без прежних/новых значений, и этот список не означает фактическое изменение. Для восстановления истории нужен согласованный diff. Паспортные и банковские данные нельзя механически дублировать в общедоступной истории; заранее определить допустимые поля и доступ к ним. Автомобили, напротив, сохраняют полный before/after, хотя UI показывает diff: можно хранить только изменившиеся значения.

### Приоритет 2 — небольшое укрепление модели

4. **Удалить дублирующие уникальные индексы справочников.** Для марки достаточно уникального `lower(trim(name))`; для модели — пары `brand_id, lower(trim(name))`. Обычные уникальные `name` / `brand_id,name` не добавляют защиты к этим более строгим ограничениям, но обслуживаются при каждой записи. Нормализация внутренних пробелов сейчас только в API; её контракт стоит закрепить при будущих импортах.
5. **Тип процедуры отделить от отображаемого текста, если появятся расчёты по журналу.** Сейчас это свободная строка, а UI распознаёт ТО по точному значению «ТО». На текущем этапе свободный ввод полезен. Для отчётов о последней замене масла/ГРМ и интервалах нужен стабильный `procedure_code` плюс свободное название/пометка; иначе варианты написания разобьют одну процедуру на разные группы. Не стоит делать закрытый enum всех возможных работ.
6. **Добавить адресные CHECK.** Положительная версия, непустые названия справочников/процедур/заметок, согласованность `is_active`, `resolved_at`, `resolved_by` заметки, допустимые статус и число попыток outbox. Сейчас часть инвариантов обеспечивает только API. Проверки паспортов не обязательно целиком копировать в SQL.
7. **Обязательность коробки согласовать между UI и API.** UI требует выбор, API допускает NULL для совместимости со старыми машинами. Сначала заполнить старые записи, затем при необходимости сделать NOT NULL и обязательный DTO. Нельзя подставлять АКПП или МКПП без данных.

### До реальной эксплуатации / при росте

8. **Определить назначение и жизненный цикл outbox.** Сейчас изменения клиентов/автомобилей создают pending-события, но в реализованном API нет worker, который их обрабатывает. Outbox оправдан для будущих PDF/писем; не нужно бессрочно складывать туда каждое CRUD-событие без потребителя. Перед запуском фоновых задач определить обработчики, повторы, окончательные ошибки и очистку обработанного.
9. **Определить сроки хранения служебных данных.** Для истёкших сессий, лимитов входа, результатов команд и завершённых заданий нет общей фоновой очистки. Срок идемпотентности должен быть частью контракта: удаление результата снимает защиту от очень позднего повтора. Аудит не удалять по тем же правилам, что сессии.
10. **Индексы добавлять по запросам и объёму.** Подстрочный поиск через `strpos(lower(...))` при росте потребует изменения запросов/индексов, но на небольшом автопарке массовое индексирование всех флагов бессмысленно. Индекс журнала `(vehicle_id, performed_on)` можно расширить полями сортировки при заметном объёме. FK сами по себе не требуют индекса на каждом столбце; оценивать реальные join/delete/update.

## Ограничения нумерации

ID уникален только внутри своей таблицы. Ссылки, ключи событий, кеши и аудит должны включать контекст сущности; outbox уже использует действие с префиксом сущности. Числовые ID не заменяют контроль доступа. Пропуски после отката транзакций допустимы: это технические ключи, а не сквозная нумерация договоров или бухгалтерских документов.

Отдельные последовательности упрощают модель, но не уменьшают уже выданные номера. Сохранение старых ID означает, что в некоторых таблицах нумерация продолжится с пятизначных значений. Новые пустые таблицы начнут с 1.
