Сквозные финансовые API и фактический жизненный цикл ниже остаются целевым проектом; их наличие в этом документе не означает реализацию. ID сущностей — number; UUID ключей команд и трассировки не являются ID карточек.

Минимальный пробег при досрочном возврате: `calculatedMileageLimitKm = dailyMileagePackageKm × max(1, contractDays)`. При `contractDays=0` сохраняется один суточный пакет, без добавления оплачиваемых суток. `effectiveMileageLimitKm` по-прежнему равен явному индивидуальному override, включая 0, либо расчётному лимиту. Версия правил — `tz-1.1-q17-v5-minimum-mileage-package`.

Досрочный возврат (`operationKind=early_return`) по новому правилу пользователя: полные использованные сутки + MAX(остаток часов, перепробег). `contractDays` может быть 0; часы не округляются в новые полные сутки. Ответ дополняется `earlyReturn {originalReturnAt,actualReturnAt,fullDays,remainingFullHours}`, `pricingBasis` и `refundOrCreditIfFullyPaidRub`. В этом сценарии `lateCandidateRub` — стоимость часов после полных суток, а `agreedReturnAt` — граница оплачиваемых полных суток. Возврат/зачёт вычисляется условно для полной оплаты прежнего итога; фактические деньги проверяются будущим Finance. Пример: 11 суток по 1200 ₽ → факт 6 суток 3 часа → 8100 ₽, уменьшение на 5100 ₽ при отсутствии остальных доплат. Подтверждение сохраняет только новый снимок, не выплату.

Защита продления: `nonBillableDays`, если передан, содержит полный список «Вых» новой редакции. Состав и причины в уже согласованных сутках должны точно совпадать с исходным снимком; пропуск поля сохраняет их. Изменение старой части в `extension` отклоняется `422 AGREED_DAYS_LOCKED`; намеренное изменение выполняется отдельной операцией `non_billable_day`/`adjustment`. При продлении новые скидки относятся только к добавленным суткам, прежние скидки сохраняются в `calculation.discounts[]` с диапазонами действия. Сервер дополнительно сверяет стоимость прежнего периода с подтверждённым итогом (`AGREED_PRICE_LOCKED`).

Уточнение 13 ноября: ручная цена в POST `/pricing/quote` — `overrides.customDailyRateRub` (строка целых рублей **за сутки**). Итог вычисляется сервером по оплачиваемым суткам; ставка опоздания автоматически берётся из последних согласованных суток. Прежние входные `customTotalRub` и `lateDailyRateRub` не принимаются. Сохранённые старые снимки читаются без изменения; для перехода к новым условиям требуется явная редакция цены. [Правила и совместимость](stage-3.md).

13 ноября 2026: реальные API этапа 3 — GET `/pricing/catalog`, GET `/pricing/quotes?page=1`, GET `/pricing/quotes/:id`, POST `/pricing/quote`, POST `/pricing/quotes/:id/confirm`; восстановление через `/operations/by-key` для `pricing.quote` и `pricing.confirm`. [Точный контракт и ограничения](stage-3.md). ID — number, суммы — десятичные строки. Подтверждение сохраняет только снимок расчёта. Booking/schedule API реализованы по ссылкам выше; lifecycle endpoints ниже остаются проектными; реализованный контракт Finance указан в отчёте этапа 5. Ошибки входного DTO текущего API возвращают 400; нарушения бизнес-правил — 422; версия/истечение — 409.

Актуальное изменение: идентификаторы записей в URL — положительные числа, в JSON — number. Прежнее описание UUID ниже заменено [решением о числовых ID](numeric-ids.md).

Текущее состояние после этапа 2: реальные маршруты клиентов, автомобилей, справочников и бизнес-команд перечислены в [stage-2.md](stage-2.md). Общий контракт ниже описывает также будущие этапы; исходное утверждение об отсутствии всех бизнес-маршрутов теперь историческое.

## Правила обмена

Префикс `/api/v1`. Даты — ISO 8601 с часовым поясом; суммы — строки целых рублей (суффикс Rub), дробные суммы запрещены; ID сущностей — number. DTO не совпадают с таблицами БД: отсутствуют password_hash, session token hash, приватные storage keys, внутренние данные очереди. Сервер проверяет размеры, обязательность, диапазоны и неизвестные поля.

Сессия сотрудника — cookie. Для изменяющих запросов требуется CSRF-защита. Права проверяются на сервере для каждого действия и ресурса. Сервер может вернуть `allowedActions` для интерфейса, но всё равно повторяет проверку при выполнении.

Команды создания/подтверждения/выдачи/оплаты/возврата/отправки письма принимают `Idempotency-Key`. Редактирование принимает `expectedVersion` соответствующего агрегата: этот вариант выбран вместо смешивания HTTP If-Match с собственными кодами конфликта. При желании перейти на ETag контракт необходимо согласовать целиком.

Успех: 200 для чтения/команды, 201 для создания ресурса, 202 для принятого задания PDF/письма. Ошибки: 400 — неверная структура; 401 — нет сессии; 403 — нет права; 404 — нет доступного ресурса; 409 — версия/расписание/ключ команды конфликтуют; 422 — не выполнено бизнес-условие; 503 — временная недоступность.

```json
{
  "code": "BOOKING_VERSION_CONFLICT",
  "message": "Запись изменена другим сотрудником. Обновите данные перед сохранением.",
  "details": { "currentVersion": 8 },
  "requestId": "..."
}
```

После сетевого сбоя результат проверяется через `GET /operations/:id` или `GET /operations/by-key?key=...&command=...` в пределах прав текущего сотрудника. В операционном ответе — состояние и ссылка на результат без чужих персональных данных. Отсутствие записи не означает автоматически, что исходный запрос уже не исполняется; повтор разрешается тем же ключом после проверки, с серверной дедупликацией.

Все маршруты кроме login, ограниченной фото-ссылки и согласованных health-проверок требуют сессию. Публичный маршрут `GET /shared/damage-photos/:token` использует отдельную capability-проверку и никогда не обращается к личным документам. Токены исключаются из access logs; страница без сторонней аналитики, с `Referrer-Policy: no-referrer` и запретом кэширования приватного ответа.

Frontend `/clients` использует API `/customers`, как в ТЗ; это осознанное различие, а не две сущности клиента. `/users` — frontend route, `/admin/users` — защищённый API. Менеджер имеет доступ к расходам, инкассациям, сверкам, штрафам и долгам, но не к созданию пользователей. Перед подтверждением новой брони и выдачей по существующей сервер повторно проверяет блокировку клиента под общей с командой block/unblock блокировкой строки.

Точные CRUD-маршруты ещё могут уточняться. Принципиальные изменения относительно списка ТЗ: осмотры/PDF доступны через booking до выдачи; нет произвольного PATCH финансовой истории или присваивания статуса брони; досрочная сдача — вариант единой команды check-in, а не независимое второе закрытие.

### Автомобиль с назначенными бронями

`GET /vehicles/:id` возвращает `activeBookingIds` — ID подтверждённых броней с действующим назначением этой машины, у которых интервал назначения ещё не закончился. Список отсортирован по началу назначения, затем по ID брони.

Архивирование и смена модели такого автомобиля возвращают `409 VEHICLE_HAS_ACTIVE_BOOKINGS` с `details.bookingIds`. Оператор открывает бронь, выбирает замену и затем повторяет изменение автомобиля. Обычные правки карточки, включая изменение готовности, доступны при действующих назначениях.

## Создание брони

Для новой брони организации `POST /bookings` принимает необязательное поле `requestAccountingEmail`. При значении `true` и действующем назначении задание `booking.accounting-email` сохраняется вместе с бронью, а ответ содержит `accountingEmailRequested: true`. При создании без машины задание не создаётся. Последующее назначение не инициирует отправку.

`POST /bookings/:id/accounting-email` с `expectedVersion` ставит письмо в очередь по действующему назначению подтверждённой брони организации. Команда использует ключ идемпотентности. После подтверждённого SMTP-приёма повторная команда не создаёт письмо. В письмо входят название организации, даты, стоимость из последнего расчёта, марка, модель и госномер. Реквизиты операторы отправляют отдельно.

`GET /bookings/:id/accounting-email` возвращает `canRequest` и `status`: `none`, `pending`, `running`, `done`, `failed`, `unknown` или `cancelled`. `done` означает принятие письма SMTP-сервером. Задание в ожидании без привязки к действующему назначению возвращает `none`. Его можно запустить явной командой при наличии машины.

Ответ также содержит `isCompany` и `sentAt` (ISO 8601, `null` до успешной отправки). В `GET /calendar` элементы `events` и `unassignedBookings` для брони организации без подтверждённой отправки содержат `accountingEmailUnsent: true`.

Пример тела, имена полей — проектные:

```json
{
  "customer": { "new": { "type": "individual", "displayName": "Тестовый клиент" } },
  "target": { "type": "model", "id": "<uuid>" },
  "pickupAt": "2026-12-01T10:00:00+03:00",
  "returnAt": "2026-12-04T10:00:00+03:00",
  "pricing": { "tariffPlanId": "<uuid>", "contractDays": 3, "billableDays": 3 },
  "confirm": true,
  "riskAcceptance": null
}
```

`customer` — взаимоисключающие варианты `existingId` и `new`. `target` — объединение vehicle/model/brand/equivalence_group. Сервер сам вычисляет тариф; клиент не передаёт произвольную доверенную итоговую сумму. Индивидуальная корректировка — отдельное явное поле с причиной и проверкой права.

Quote возвращает `dailyMileagePackageKm`, `contractDays`, `billableDays`, `calculatedMileageLimitKm`, `effectiveMileageLimitKm` и основание ручного override. Например, 250 км/сутки × 3 суток = 750 км; один «Вых» не уменьшает 750 км. При приёмке ответ содержит `lateCandidateRub`, `mileageCandidateRub`, `selectedSurchargeRub = max(...)` и версию расчёта. По согласованному Q3 это одно начисление, не сумма двух. Полные дни опоздания тарифицируются по согласованной ставке, остаток 1–4 часа по 300 ₽, с 5 часов — ещё сутки. Лимит увеличивается только при отдельном продлении договора.

Если появился риск, ответ 409 `RISK_ACCEPTANCE_REQUIRED` содержит причины и непрозрачный токен оценки. Подтверждение пользователем передаёт token и reason. Сервер повторно оценивает риск под блокировкой; изменившийся набор причин требует нового подтверждения. Токен оценки не является резервом машины. Клиент и бронь создаются одной транзакцией только при успехе.

При назначении конкретной машины пересечение — 409 `VEHICLE_ASSIGNMENT_CONFLICT`; принятие риска не позволяет обойти этот запрет.

## Calendar read model

Способ доставки обновлений MVP: клиент повторяет GET нужных данных активного экрана раз в 5 секунд, а также после возвращения во вкладку/восстановления сети. SSE endpoint не проектируется для MVP. Ответы календаря ниже пока проектные; общий polling бизнес-экранов ещё не реализован. Опрос не меняет правила авторизации, expectedVersion и идемпотентности команд.

Один ограниченный по диапазону запрос возвращает:

- `vehicles`: имя модели, номер, текущие readiness/maintenance/cleaning/issue-маркеры;
- `events`: ID, тип, vehicleId, bookingId?, период, подпись клиента, paidRatio?, маркеры;
- `unassignedBookings`: брони без машины, допустимые цели и причины риска;
- `problemsCount`, `presence`, `evaluatedAt`;
- при необходимости `nextCursor` для длинного списка неназначенных броней.

Суммы и краткое финансовое состояние можно получать по отдельному summary endpoint при открытии tooltip/Popover; паспортных данных в календарном payload нет. Период одного запроса ограничивается сервером; бесконечная прокрутка реализуется окнами запросов, а не ответом за всё время.

`paidRatio` — результат Finance, а не вычисление frontend по сырым платежам. Перед выдачей тип события booking всегда жёлтый. Для технических событий отдельный тип. Фактическая просрочка и следующий план могут визуально пересекаться как конфликт; это не разрешение двойной выдачи.

## Документы и асинхронные операции

[результат этапа 6](stage-6.md).

POST версии договора возвращает ID версии и `generationStatus=pending`. После готовности сотрудник скачивает именно этот PDF. GET отсутствующего готового файла возвращает явное состояние ожидания/ошибку, а не подменяет его предыдущей версией. Повтор генерации не меняет снимок документа.

Для загрузок — ограничение числа/размера, проверка содержимого и прав на объект. Финализация загрузки и привязка к осмотру выполняются отдельно от факта успешного получения байтов. Фото для клиентской ссылки выбираются из завершённой редакции pickup; документы клиента и фото check_in исключаются серверным запросом.

Отправка письма возвращает `deliveryId` и состояние queued. Статусы: queued, sending, sent, failed, unknown. Интерфейс не показывает «письмо доставлено», если подтверждено только принятие SMTP.

Без email ответ отправки — явный `skipped/no_email`; задание SMTP не создаётся, выдача автомобиля разрешена при выполнении остальных условий. Включённый НДС 5% в PDF вычисляется как round(totalRub × 5 / 105), не прибавляется к цене и не создаёт денежную команду.

## Денежные команды v1.1

Каталог назначений задаёт `direction`, обязательные ссылки, допустимые способы и классификацию. POST `/financial-operations` принимает discriminated union, а не произвольный набор account/sign полей. Клиент не назначает операцию «выручкой» самостоятельно. Контекст аренды и модалка журнала вызывают один прикладной обработчик и создают одну financial_operation.

Для штрафа обязательны customerId и fineId; bookingId получается из штрафа и не выбирается в платёжной форме. Оплата повреждений/доплаты требует существующего начисления, клиента и аренды. Ручной долг погашается назначением `debt_payment` с выбором debtId; допустимы cash, bank, customer_credit (согласовано пользователем).

Оплата из остатка принимает сумму и разрешённые source allocations. Сервер проверяет принадлежность, ограничения замороженной части, достаточность именно клиентского остатка и актуальную задолженность. Превышение суммы долга не превращается молча в переплату. Источник deposit переводит деньги −deposit_pool/+operating_cash; источник переплаты аренды, уже находящийся в кассе, не увеличивает её повторно. Смешанный остаток может потребовать несколько allocations одной команды. Остаток банковского происхождения также не превращается автоматически в наличные.

Недостаток физического фонда не запрещает операцию (ответ пользователя Q4): preview показывает итоговый отрицательный остаток, запрос требует `shortfallAcknowledged` и непустую причину. Под блокировкой фондов сервер пересчитывает последствия; при существенном изменении показанного предупреждения возвращает новый preview вместо молчаливого проведения. Это правило не разрешает отрицательный клиентский резерв или оплату сверх долга.

Сверка принимает фактический остаток, причину и версию показанного фонда. Если одновременно проведён платёж, сервер возвращает конфликт для повторной сверки. Нельзя применять разницу, рассчитанную по устаревшему остатку. Начальное сальдо имеет уникальность по фонду, блокировку режима первичного запуска и не попадает в суммы поступлений/расходов.

Журнал/итоги/экспорт используют один нормализованный фильтр и snapshot/asOf. Текущая касса возвращается отдельным полем `currentCashBalance`, независимо от фильтров журнала. Переводы, внешние поступления, расходы, инкассации и расхождения идут отдельными totals. Экспорт содержит только доступные пользователю колонки; пользовательский текст записывается как текст, а не Excel-формула.

Для разморозки нет пользовательского API «освободить любой резерв раньше срока»: внутренний обработчик проверяет releaseAt и атомарно высвобождает оставшуюся сумму. GET баланса перед ответом обеспечивает учёт истёкших резервов тем же идемпотентным обработчиком.

## Генерация клиента и ошибки

OpenAPI является транспортным контрактом. Из него генерируется `packages/api-client`; ручные query hooks размещаются в frontend поверх клиента. Сгенерированные файлы не редактируются вручную. Backend domain-модели остаются внутренними.

В CI сравнивается воспроизводимость генерации и проверяются несовместимые изменения API. Для запроса схемы используется build-time генератор, а не обязательное подключение к рабочему серверу. Общая схема ошибок, строки денег и version-поля имеют контрактные тесты.

В quote: periods[], dayLines[], old/new totals, contractDays, billableDays, effectiveMileageLimitKm, totalUsageMileageKm, lateCandidateRub, mileageCandidateRub, selectedSurchargeRub, fuelCharges[], washRub?, includedVatRub, overridesToConfirm[], warnings[], explanation[]. Цена топлива — 80 ₽/л, не вводится клиентом как доверенный параметр. Временной quote не фиксирует деньги и не гарантирует свободную машину.

explanation содержит тип правила, период, количество суток, тариф, исходную/новую сумму и понятную русскую подсказку. UI показывает «7 суток сохранены; продление сокращено с 3 до 1 суток; новая ставка …», а не только общий итог. При смене цены оператор видит рассчитанное значение и собственную корректировку отдельно.

Сервер связывает quote с версиями условий, осмотров, использования и правил; при устаревании — 409 QUOTE_STALE с новым расчётом. Команда повторяет проверки и сохраняет единственную новую редакцию; фронтенд не может прислать доверенное начисление. Дробные рубли, топливо вне 0..8 и иной кузов — 422.

NO_PICKUP_PHOTOS и OUTSIDE_OPERATING_HOURS возвращаются как предупреждения с основанием/версией; подтверждение разрешает продолжить только соответствующее предупреждение. CUSTOMER_BLOCKED, DOCUMENTS_NOT_READY, SIGNATURE_CONFIRMATION_REQUIRED и недоступность машины остаются запретами.

Возврат банковского источника наличными — 422 REFUND_METHOD_MISMATCH; preview показывает source allocations. Нулевая цена даёт полное финансовое покрытие без создания операции. Calendar добавляет nonBillableDays с rentalDayIndex и границами, завершённые события получают актуальную финансовую окраску.

Фото API возвращает deleteAfter/deletedAt и явный статус expired/deleted без storage key. После срока файлы и публичные ссылки недоступны независимо от worker; документные endpoints не возвращают бессрочную копию удалённых фото.
