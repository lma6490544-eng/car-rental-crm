# Правила разработки CRM

- Читаемость и поддерживаемость важнее минимального количества строк. Соблюдай существующие границы NestJS-модулей, страниц React и предметных сервисов.
- Не объединяй независимые инструкции в одну строку. Для связанных объявлений также предпочитай отдельные строки, если это упрощает чтение.
- Используй понятные предметные имена функций, типов и переменных (`customer`, `note`, `changePage`). Короткие индексы допустимы в небольших локальных циклах.
- Многошаговые inline-обработчики выноси в именованные функции. Простые вызовы и переключения состояния допустимы inline. Избегай вложенных тернарных выражений и условий, требующих мысленного восстановления порядка действий.
- Разделяй ответственность по смыслу: редактор, вкладка, запрос, расчёт. Не создавай компоненты, хуки, универсальные формы или репозитории только ради сокращения файла. Небольшие понятные компоненты не дроби.
- Отделяй преобразование формы и расчёты от представления, когда это упрощает проверку. Состояние одного сценария держи рядом; не вводи новые состояния, если значение можно вычислить из существующих.
- Описывай известные ответы API, строки SQL, формы и props конкретными типами. Сетевые DTO со строковыми датами отделяй от строк PostgreSQL с `Date`. Для неизвестных данных используй `unknown` и сужение. Не заменяй `any` бессодержательным индексным типом или двойным приведением ради прохождения линтера.
- У эффектов должны быть все реактивные зависимости. Если эффект намеренно запускается только при смене сценария, отделяй чтение актуального состояния от запуска эффекта; не расширяй зависимости ценой сброса открытой формы. Сохраняй очистку таймеров, подписок, запросов и защиту от устаревших ответов. Не подавляй правила Hooks.
- При рефакторинге сохраняй API, валидацию, маршруты, ключи компонентов, снимки версий, polling, блокировки, порядок транзакций, ключи идемпотентности и повторную отправку. Не меняй интерфейс и поведение под видом улучшения стиля.
- Не меняй схемы БД и миграции в задачах читаемости. Не форматируй `drizzle`, зависимости, сборки, generated-файлы, `.runtime`, `.local` и `outputs`.
- Перед массовыми изменениями обеспечь откат. Не трогай несвязанные изменения пользователя; не смешивай форматирование и содержательный рефакторинг в одном коммите.
- Не обновляй зависимости без отдельного согласования и не запускай `npm audit fix` автоматически. Не ослабляй ESLint ради формального прохождения проверок.
- Автоматически форматируй изменённые исходники Prettier. `npm run format` форматирует весь проект; в небольшой задаче передавай Prettier только изменённые пути.
- После изменений запускай `npm run check` (Prettier, ESLint без предупреждений, TypeScript). Для проверки сборки используй `npm run build`.
- Запускай релевантные тесты: `npm run test:api`, `npm run test:web`, либо весь набор `npm test`. Интеграционным тестам нужны локальная PostgreSQL и браузер Edge/Playwright. Сообщай точные результаты и оставшиеся проблемы; не меняй тесты ради зелёного результата.

## Backend — `apps/api`

- До изменения сценария сверь действующие правила в [API-контракте](docs/api-contract.md), [модели данных](docs/data-model.md) и принятом продуктовом решении. При намеренном изменении поведения обнови соответствующий контракт и тест вместе с кодом. Для обычной правки достаточно описания изменения и результатов проверок, отдельный отчёт о переносе метода не нужен.
- Оставляй в HTTP-контроллере разбор запроса и формирование ответа. У сложного сценария должен быть понятный владелец. Переиспользуй существующий расчёт в preview и при сохранении. Называй функции, которые делают записи, так, чтобы вызывающий код видел этот эффект.
- Для идемпотентной бизнес-команды используй `CommandsService.run`. Передавай выданный им `PoolClient` во все вложенные операции, включая SQL для аудита и outbox. Повторно проверяй права, версии и предметные ограничения внутри транзакции под соответствующими блокировками. Учитывай повтор всего callback при deadlock. Внешнюю отправку и обработку файлов выполняй после фиксации через outbox.
- Если несколько запросов формируют один согласованный ответ, установи `REPEATABLE READ` до первого чтения и передавай один клиент всем участникам. Ориентир — [карточка брони](apps/api/src/scheduling/booking-query.service.ts). Кэш подготовленных фактов календаря ограничивай текущим запросом и его снимком.
- Проверяй инвариант со стороны каждой команды, способной его нарушить. Назначение машины, смена её модели и архивирование используют общий schedule lock. Для `vehicles.*` его берёт [исполнитель команд](apps/api/src/platform/commands.service.ts) по имени команды. При добавлении или переименовании команды проверь порядок advisory и row locks и повторную проверку после ожидания. UI должен объяснять отказ и давать оператору доступное действие, API самостоятельно отклоняет конфликтующий запрос.
- Выводи тип строки SQL из проекции запроса, миграций, nullable-колонок, JOIN и преобразований драйвера. Указывай фактический результат `RETURNING`. Generic `query<T>` и приведение JSONB не проверяют данные в runtime. Проверяй отдельно черновые, подтверждённые и исторические строки, если их форма различается.
- Для финансов передавай рублёвые суммы строками через API и считай через `BigInt` с проверкой диапазона. Сохраняй идентичность источника и физического фонда при возврате и компенсации. Не восстанавливай неизвестный фонд по догадке. При изменении правила сверь preview, post и откат поздней ошибки.
- Выбирай проверки по риску. Для гонки используй два соединения с временной PostgreSQL-БД и управляемую точку конкурентной записи. Для составного GET проверь целостность текущего ответа и видимость изменения в следующем. Для команды проверь состояние БД после отказа и повтора. Для изменения процесса оператора пройди его в браузере. Проверяй наблюдаемое поведение; замороженные исходники нужны только при обоснованной необходимости сравнения.

## Frontend — `apps/web`

- Применяй общие правила выше ко всему React/TypeScript-коду. Формат задаёт `.prettierrc.json`, проверки — `eslint.config.mjs` и `apps/web/tsconfig.json` (`strict`). Не подменяй эти настройки собственным стилем.
- До написания кода изучи связанные реализации и выбери расположение новых файлов; для сложной задачи определи основные ответственности и зависимости. Для тривиального изменения подробный план не нужен.
- Уменьшай вложенность с помощью early returns, когда это улучшает чтение. Обработчикам событий давай понятные имена по действию (`handleSubmit`, `handleChange`, `handleClose`), сохраняя соглашения окружающего кода.
- Сохраняй структуру `src/pages/`, `src/features/`, `src/shared/`, `src/domain/`: страницы собирают экран; features содержат функциональность сценариев; shared — общие UI, хуки и утилиты; domain — предметные типы и правила. Компоненты, хуки и преобразования конкретной страницы держи рядом с ней, переиспользуемые модули — в соответствующем общем каталоге. Существующие общие модули в корне `src/` не переноси без необходимости задачи.
- Не импортируй общие сущности через файлы страниц и не создавай циклические зависимости. Перед добавлением модуля проверь соседние реализации и общие `api.ts`, `catalog.tsx`, `formats.tsx`, `shared/`, `domain/`, `features/`.
- У компонента должна быть понятная ответственность. Выделяй самостоятельные части, когда это облегчает чтение, тестирование или переиспользование; ориентируйся на смысл, а не число строк. Сложную бизнес-логику и асинхронные сценарии выноси из JSX в именованные функции; самостоятельную логику состояния и эффектов — в кастомный хук, когда это оправдано. Не создавай абстракции и файлы ради формального дробления.
- Предпочитай композицию компонентов сложной конфигурации через props. Не превращай общий компонент в набор условных режимов, если это затрудняет понимание его контракта.
- Соблюдай Rules of Hooks: вызывай хуки только на верхнем уровне React-компонентов и кастомных хуков, без условий, циклов и вызовов из обработчиков. Текущий ESLint не проверяет Hooks автоматически; проверяй это при чтении изменений.
- Используй `useEffect` для синхронизации с внешними системами, а вычисляемые значения получай при рендере; действия пользователя обрабатывай в обработчиках. Добавляй `useMemo` и `useCallback` только при понятной необходимости, а не по умолчанию. Правила зависимостей, очистки и производного состояния заданы выше.
- Для запросов обрабатывай загрузку и ошибки; при смене параметров или размонтировании отменяй запрос либо игнорируй устаревший ответ. Разделяй независимые асинхронные сценарии, когда это упрощает управление их жизненным циклом и предотвращение гонок. Используй существующие механизмы API и polling, сохраняя защиту пользовательского ввода и повторной отправки команд.
- Для состояний с различающимися контрактами предпочитай discriminated unions. Переиспользуй типы при совпадении семантики; не вводи сложные generic-типы без практической необходимости. Общие требования к конкретным типам, `unknown` и безопасному сужению заданы выше.
- Используй семантически корректные элементы и обеспечивай управление с клавиатуры, видимый фокус и подписи полей. Учитывай disabled/loading/error и управление фокусом при открытии и закрытии диалогов. Сначала используй подходящие компоненты проекта и возможности применяемой UI-библиотеки; не создавай собственный сложный контрол без необходимости. Меняй визуальный дизайн и UX только в рамках задачи.
- Переиспользуй бизнес-правила, расчёты и преобразования данных; не копируй серверные финансовые формулы во frontend. Не объединяй похожие реализации, если различаются их контракты или семантика.
- Реализуй согласованный объём полностью: не оставляй заглушки, фиктивную логику или TODO вместо реализации без явного согласования. Обрабатывай ожидаемые ошибки и пограничные случаи; не скрывай ошибки пустыми `catch` или необоснованными значениями по умолчанию.
- Перед завершением проверь читаемость и ответственность компонентов, отсутствие лишних абстракций и дублирования, размещение новых файлов, направление импортов и отсутствие ненужных зависимостей. Выполни общие проверки выше и применимые связанные frontend-тесты; сообщи, какие команды запускались, их результаты и причины пропуска остальных. Невыполненные проверки не называй успешными.
